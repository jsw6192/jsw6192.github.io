본문으로 바로 가기
성인용 · 15세처럼 쉽게

AI에게 일을 시키는 게 아니라,
일하는 체계를 만든다.

이 프로젝트는 검사 몇 개를 설치하는 도구가 아니다. 서로 다른 저장소에서 AI와 사람이 어떤 정보를 읽고, 누가 결정하고, 무엇이 실제로 실행됐는지 연결해 주는 저장소 내장형 AI 작업체계를 연구한다.

현재아이디어를 검증하는 초기 골격. 완성품이 아니다. 목표저장소마다 다른 조건을 읽고, 맞는 구성을 설명하며, 안전하게 적용하는 체계.
왜 필요한가 어디에 쓰나 어떻게 움직이나 무엇이 들어가나 왜 톱니바퀴인가 예시 제약의 제약 오해 금지 어떻게 증명하나
01 · 문제

규칙 파일이 있다고 체계가 있는 것은 아니다.

AI 지침, 역할, 훅, CI가 파일로 존재해도 실제로 읽히거나 실행되지 않을 수 있다. 반대로 규칙이 너무 많으면 중요한 작업을 방해해 사람들이 우회하기 시작한다. 이 프로젝트는 “있다”와 “작동한다”를 분리해서 본다.

지금 있는 것

  • 저장소를 읽기 전용으로 조사하는 도구
  • 일부 로컬 Git 훅과 범용 검사기
  • 설치·제거를 시험하는 초기 코드
  • 여러 안전 결함을 드러낸 합성 테스트

만들려는 것

  • 저장소마다 다른 환경을 기능 수준에서 진단
  • 정말 필요한 질문만 사람에게 요청
  • 서로 얽힌 설정의 파급 효과를 설명
  • 계획·승인·적용·검증·복구·진화를 하나의 흐름으로 연결
02 · 적용 범위

출발선이 달라도 들어갈 수 있어야 한다.

정답 세트를 복사하는 대신 현재 상태를 먼저 읽는다. 기술 스택뿐 아니라 기존 AI 체계, 사용자 선호, 위험, 남은 토큰·시간까지 입력으로 본다.

0

아무 체계도 없는 저장소

규칙 파일도 훅도 없다. 최소 골격부터 제안하되 필요하지 않은 문서와 검사를 쌓지 않는다.

½

일부만 있는 저장소

문서만 있거나 훅만 있을 수 있다. 파일 이름이 아니라 실제 연결과 실행 여부를 조사한다.

N

이미 성숙한 저장소

기존 체계를 함부로 대체하지 않는다. 소유권과 충돌을 찾고 coexistence부터 검토한다.

03 · 작동 원리

먼저 읽고, 나중에 쓴다.

대화형 AI가 마음대로 파일을 고치는 구조가 아니다. 조사와 변경을 가르고, 승인된 계획과 실제 결과가 같은지 다시 확인한다.

  1. 관측현재 파일·Git·훅·CI·도구를 읽기만 한다.
  2. 분류사실, 추론, 사람의 결정, 모르는 것을 나눈다.
  3. 질문관측으로 못 정하고 결과를 바꾸는 것만 묻는다.
  4. 후보 계획추가·삭제·동기화될 항목과 이유를 보여 준다.
  5. 승인정확한 계획과 영향 범위에 결정을 묶는다.
  6. 적용허용된 경계 안에서 원자적으로 바꾼다.
  7. 검증실제 적재와 실행을 다른 관측 경로로 확인한다.
  8. 진화새 증거는 후보가 되고, 반증·승인 뒤에만 정책이 된다.
04 · 구성

게이트는 전체의 한 부품이다.

저장소에서 AI가 잘 일하려면 “막는 검사”만으로는 부족하다. 읽을 정보, 맡을 역할, 사용할 모델, 검토 방식, 실패 뒤의 복구와 학습까지 연결돼야 한다.

저장소의 현재 사실코드 · 문서 · Git · 사람의 결정 · 미결
진단과 질문
무엇이 있고 무엇을 모르는지 찾는다.
문맥과 프롬프트
필요한 정보만 실제로 적재됐는지 확인한다.
역할과 협업
누가 lead이고 누가 어떤 축을 반박하는지 정한다.
훅과 CI
로컬 피드백과 공유 강제를 구분해 연결한다.
트랜잭션
계획 밖 변경과 부분 실패를 막고 증거를 남긴다.
모델 라우팅
필요 능력을 추천하되 권한과 성능을 교환하지 않는다.
증거와 검증
안 돈 검사와 확인 불가를 성공에서 분리한다.
정책 진화
사고를 규칙으로 바로 굳히지 않고 시험·만료·철회한다.
05 · 관계형 커스터마이징

설정은 체크박스가 아니라 관계다.

예를 들어 토큰이 적다고 검토를 그냥 끄면 위험하다. 작업 범위를 줄이거나 나누고, 안전 하한을 못 지키면 중단해야 한다. 조정 결과뿐 아니라 왜 함께 바뀌었는지를 보여 준다.

requires
A를 켜면 B가 반드시 필요하다.
forbids
A와 B를 동시에 쓸 수 없다.
synchronizes
A가 바뀌면 B도 함께 갱신돼야 한다.
substitutes
A가 이미 같은 일을 하면 B를 중복 설치하지 않는다.
shares_budget
문맥·검토·시간이 같은 한정 자원을 나눠 쓴다.
compensates
A를 줄였으면 다른 장치로 빈자리를 보완한다.
invalidates
A가 바뀌면 과거 검증 결과가 더는 유효하지 않다.
erodes
설정은 켜져 있지만 우회 때문에 실제 효과가 약해진다.
common_mode
서로 다른 방어처럼 보여도 같은 원인으로 함께 틀린다.
06 · 구체적인 예

학교 팀 프로젝트 저장소라면?

다섯 명이 웹 서비스를 만들고 AI도 함께 쓴다고 가정한다. 프로젝트에는 짧은 시간이 남았지만 로그인 정보를 다루기 때문에 안전 검사를 없앨 수는 없다.

관측된 상황

React 프런트엔드와 Python 서버가 한 저장소에 있고, 팀원마다 다른 AI를 쓴다. `AGENTS.md`는 있지만 실제로 모든 도구가 읽는지는 모른다. 로컬 훅은 한 명에게만 있다.

시스템은 “강한 설정으로 전부 설치할까요?”라고 묻지 않는다.

진단두 스택, 여러 AI, 공유되지 않은 훅, 인증 데이터 위험을 찾는다.
질문누가 정책을 승인하는지, CI를 쓸 수 있는지처럼 관측 불가능한 것만 묻는다.
관계시크릿 검사 활성화는 공유 CI와 실제 검사기 배포를 필수화한다.
자원토큰이 부족하면 문맥을 요약하고 작업을 나누되 필수 검사는 내리지 않는다.
결과후보 계획과 파급 효과를 보여 주고, 승인 뒤 적용·검증한다.
07 · anti-ratchet

제약도 스스로 증명해야 한다.

사고가 날 때마다 금지와 승인 절차를 더하면 시스템은 굳는다. 안전 규칙도 누구를 무엇으로부터 지키며, 실제 비용이 얼마인지 설명해야 한다.

“안전 하한은 몰래 낮추지 않는다. 그러나 하한을 지키는 방법은 검토하고 바꿀 수 있다.”
  • 모든 제약은 근거, 범위, 소유자와 발동 조건을 가진다.
  • false block과 안전한 작업이 막힌 시간을 측정한다.
  • 만료, 재심, 완화·삭제 기준을 함께 둔다.
  • 전체 교착 대신 격리·읽기 전용·별도 복구 승인 같은 안전한 탈출 경로를 둔다.
  • 자원 부족을 이유로 필수 안전을 조용히 해제하지 않는다.
08 · 오해 금지

이 체계가 약속하지 않는 것

그래프와 영수증은 연결과 실행 사실을 보여 줄 수 있다. 진실, 정당성, 안전 자체를 자동으로 인증하지는 못한다.

잘못된 이해정확한 경계
AI가 사람의 의도를 알아서 컴파일한다.명시된 의도·충돌·미결을 구조화할 뿐, 숨은 가치판단을 확정하지 않는다.
검증 영수증이 있으면 안전하다.무엇이 실행됐는지를 보여 준다. 그 판단이 옳았는지는 독립 오라클이 따로 본다.
rollback이면 모든 것이 원래대로다.소유한 파일·설정은 복원할 수 있지만, 이미 보낸 메시지·배포·사람의 결정은 별도 영향이다.
AI를 여러 개 쓰면 독립 검토다.같은 자료와 실패 성향을 공유하면 함께 틀릴 수 있다. 오류 상관을 측정해야 한다.
더 강한 모델이면 더 많은 권한을 줘도 된다.모델 능력과 실행 권한은 별도 축이다. 강한 모델도 자동으로 넓은 권한을 얻지 않는다.
지금 바로 어디에나 설치할 수 있다.현재는 연구 가설과 초기 골격이다. 트랜잭션 안전을 먼저 통과해야 한다.
09 · 검증 계획

좋았다는 느낌이 아니라, 틀릴 조건을 먼저 적는다.

빈 저장소, 일부만 있는 저장소, 성숙한 저장소, 손상·적대 상태를 나눠 시험한다. 기존 최강 도구 조합보다 낫지 않으면 “새로운 시스템”이라는 주장을 버린다.

0–1주장과 임계값을 고정하고 최소 트랜잭션 안전부터 시험한다.
2–3읽기 전용 진단과 관계형 구성 합성이 실제로 더 나은지 비교한다.
4–5문맥·훅·CI의 실제 발화와 모델 라우팅의 false-low-risk를 본다.
6–8다중 AI 오류 상관, 정책 경직, 역사적 실패 메커니즘을 공격한다.
9앞 단계를 통과한 뒤에만 실제 저장소 파일럿과 장기 추적을 연다.
평균으로 상쇄할 수 없는 즉시 실패: 승인 없는 정책 활성화, 무권한 변경, 저장소 밖 변경, 거짓 VERIFIED, 민감값 유출, 필수 안전 하한의 조용한 완화.
마지막 10단계: 전체 여정이 검증된 뒤에만 개인 전역 규칙 저장소 `.agents`의 메인 세션과 여러 차례 대화하며 적용한다. 구현을 복사하거나 활성 세션을 덮지 않고, 진단→질문→작은 적용→검증을 단계마다 반복한다.
10 · 짧은 용어집

정확한 이름으로 다시 보기

비유는 입구일 뿐이다. 실제 설계에서는 아래 용어로 상태를 구분한다.

증거 그래프와 제어 그래프

규칙·근거·문맥·역할이 어떻게 이어지는지와, 훅·CI·승인이 실제로 어디서 강제되는지를 연결한 관계 모델이다. 그래프 자체가 진실을 보증하지는 않는다.

후보 정책과 활성 정책

새 아이디어는 먼저 후보가 된다. 반증, 영향 검토, 권한 있는 승인을 거쳐야 실제 적용되는 활성 정책이 된다.

postcondition

명령이 성공 코드를 냈는지가 아니라, 실제 파일·Git 설정·실행 결과가 계획대로인지 사후에 확인하는 조건이다.

not-run · blocked · unverifiable

검사가 안 돌았음, 안전·권한 때문에 막혔음, 증거가 없어 확인할 수 없음을 각각 나타낸다. 어느 것도 성공이 아니다.

anti-ratchet

제약이 사고 때마다 추가되기만 하고 사라지지 않는 현상을 막는 원칙이다. 규칙도 비용과 실패를 측정하고 만료·재심·삭제될 수 있어야 한다.
