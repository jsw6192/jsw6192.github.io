제품명미정. 현재 저장소 이름은 임시 이름이다
구현 상태연구 가설을 검증하는 초기 골격. 완성 시스템이 아니다

이 문서는 이 저장소가 결과적으로 무엇을 만들려는지를 정한다. 기능 목록이나 현재 구현을 정당화하는 문서가 아니다. 이후 설계·실험·구현이 이 문서와 충돌하면, 충돌을 숨기지 말고 이 문서를 명시적으로 개정하거나 해당 변경을 중단한다.

1. 한 문장 정의

이 저장소는 저장소의 현재 사실, 과거 사고, 사람의 명시된 의도와 미결 사항, 실행 환경과 가용 자원을 입력으로 받아 문맥·프롬프트·역할·권한·작업·검토·게이트·CI·검증·진화가 서로 어떻게 의존하는지를 설명 가능한 관계 그래프로 모델링하고, 각 저장소에 맞는 후보 구성을 제안·적용·검증·복구하는 저장소 내장형 AI 작업체계를 만든다.

새 증거가 생겼다는 이유만으로 활성 정책을 스스로 바꾸지는 않는다. 후보와 활성 정책을 분리하고, 영향·근거·권한·철회 조건을 확인한 뒤 허용된 범위에서만 승격한다.

2. 출발점과 궁극적 목표

출발점은 public-data-diagnostics(이하 PDD)에서 실제 개발을 거치며 형성된 AI 협업 시스템이다. PDD에는 문서 계층과 지도, 역할과 브리프, 훅과 CI, 검토 절차, ADR, 자율 판단 경계, 실패에서 생긴 검사기가 서로 연결되어 있다. 여기서는 그 도메인 내용을 복사하지 않고, 시행착오에서 드러난 일반화 가능한 작동 원리와 실패 구조를 추출한다.

궁극적 목표는 PDD 복제품이나 범용 게이트 설치기가 아니다. AI 관련 체계가 전혀 없는 저장소부터 일부 규칙만 있는 저장소, 이미 거대한 자체 체계를 가진 저장소까지 진단하고, 서로 다른 기술 스택·아키텍처·조직·사용자 성향·위험도·잔여 자원에 맞춰 전체 AI 작업 시스템을 함께 조정할 수 있는 새로운 범분야 체계를 검증하며 구축하는 것이다.

현재 증거로 이 체계의 새로움·범용성·안전성은 입증되지 않았다. 새로움의 후보는 개별 부품이 아니라 다음 연결이 만드는 비가산 효과다.

  1. 실제로 적재된 문맥과 실제로 발화한 강제 장치의 연결
  2. 규칙·사고 오라클·실행 영수증·철회 조건의 연결
  3. 후보 정책과 활성 정책 사이의 권한·버전·재심 경계
  4. 저장소 상태와 사용자·자원 제약을 함께 푸는 관계형 구성 합성

동일 자원으로 구성한 기존 도구 조합이 같은 결과를 낸다면 새로운 시스템 원리라는 주장은 축소하거나 폐기한다.

4. 현재 확인된 사실과 아직 가설인 것

증거 강도는 E0 아이디어·비유·AI 합의, E1 버전된 설계·스키마, E2 합성 repo의 양성·음성 시험, E3 한 실제 repo의 재현 관측, E4 여러 repo의 사전 정의 지표, E5 맹검 비교·반례 주입, E6 장기 추적으로 구분한다. 현재 근거는 대부분 E1~E3이며 E4 이상은 아직 없다. 따라서 범용성·장기 효과·인과 우월성을 현재 사실로 쓰지 않는다.

확인된 사실

  • 현재 구현은 scan, install, uninstall, 로컬 훅과 일부 범용 검사기를 가진 초기 골격이다. 역할, CI, 정책 승격, 관계형 구성 합성, 모델 라우팅 전체는 구현되지 않았다.
  • 현재 구현에는 티어 조합, 재설치 수렴, 삭제 실패, 테스트 경로 안전성, 원자 적용과 postcondition 등에 확인된 결함이 있다. 외부 저장소 설치를 확대하기 전에 고쳐야 한다.
  • PDD의 체계는 풍부하지만 프로젝트 전용 검사기·경로·운영 가정도 함께 가진다. PDD에서 작동했다는 사실만으로 범용성이 성립하지 않는다.
  • 다중 AI를 호출했다는 사실은 독립 검토를 증명하지 않는다. 공통 학습·프롬프트·오라클· 인센티브 때문에 오류가 상관될 수 있다.

연구 가설

  • 관계 그래프로 문맥과 강제 장치의 실제 연결을 함께 추적하면 거짓 완료와 조용한 미실행을 줄일 수 있다.
  • 단계형 프리셋보다 제약과 결합 관계를 푸는 구성 합성이 다양한 저장소에 더 잘 적응한다.
  • 사고에서 나온 반례를 후보 정책으로 만들고, 독립 반증과 승인 뒤에만 승격하면 장기 학습이 가능하다.
  • 작업 특성과 가용 자원을 이용해 모델·추론 프로필을 추천하면 품질 하한을 지키면서 비용과 토큰을 줄일 수 있다.

가설은 docs/실험_계획.md의 실패 조건에 걸리면 축소하거나 폐기한다.

5. 시스템 경계

이 시스템은 저장소 범위의 제어면이다. 다음을 소유한다.

  • 저장소 진단과 질문 생성
  • 목표 구성과 현재 구성의 차이, 충돌, 미확인 상태
  • 저장소 안의 AI 지침·문맥·프롬프트·역할·검토·게이트·CI 어댑터
  • 적용 계획, 파일·Git 설정 변경, 설치 매니페스트, 검증 영수증
  • 후보/활성 정책의 버전과 승격·철회 기록
  • 모델 선택 요청과 실제 실행 프로필의 영수증

다음을 소유하거나 보증하지 않는다.

  • 사실의 진실성, 의미 안전성, 법적 적합성, 의료·군사·정치적 정당성 자체
  • 저장소 밖 서비스, 조직 권한, 사람의 이해와 동의, 이미 전달된 정보
  • 외부 메시지·배포·소비된 프롬프트·파생 clone을 포함한 완전한 rollback
  • AI 검토자의 독립성 또는 강한 모델의 정확성

저장소 밖 효과는 되돌림 가능, 보상행동 가능, 비가역 중 하나로 구분하고 별도 영향 대장에 남긴다. ROLLED_BACK 하나로 전체 사회기술 상태가 복원됐다고 표시하지 않는다.

6. 관계형 커스터마이징

커스터마이징은 단순한 T0~Tn 단계 선택이 아니다. 저장소와 사용자마다 여러 시스템이 톱니바퀴처럼 얽혀 있으므로 하나를 바꾸면 관련 부분을 다시 계산해야 한다.

6.1 입력 차원

차원예
저장소 성숙도AI 자산 없음, 일부 문서·훅 존재, 성숙한 자체 체계
아키텍처·스택단일/모노레포, 언어·빌드·패키지·배포·CI
위험과 영향변경 가역성, 피해 크기, 노출 범위, 탐지 가능성
사용자·조직개인/팀, 숙련도, 선호하는 자율성, 승인권과 이의제기 경로
자원잔여 토큰, 시간, 비용, context window, 도구·모델 availability
데이터 경계시크릿, 개인정보, 폐쇄망, provider·residency 제한
기존 체계규칙·역할·프롬프트·훅·CI·정책의 소유자와 충돌 관계

잔여 토큰과 모델 capability 같은 값은 변하는 외부 사실이다. 확인 시점과 출처를 함께 기록하고, 알 수 없거나 오래됐으면 낮은 위험으로 간주하지 않는다.

입력과 조정 손잡이를 섞지 않는다. 위 값은 조사·질의로 얻는 입력이고, 실제로 조정하는 것은 규칙의 가시성과 소유 방식, 훅 연결, 게이트 집합과 강제 지점, 문맥 배치와 예산, 검토 깊이와 정보 분리, 모델 프로필 상한, 영수증 상세도·보존, 진화 루프, 트랜잭션 강도다. 입력 사실을 사용자가 고른 설정처럼 쓰거나 사용자 선호를 repo에서 추측해 확정하지 않는다.

6.2 관계 유형

구성 요소 사이에는 최소한 다음 관계가 필요하다.

관계의미예
requires한 요소가 다른 요소를 필수화훅 활성화는 실제 검사기와 postcondition을 요구
enables선행조건이 있어야 선택 가능진입점 문서가 있어야 문맥 예산 게이트를 켤 수 있음
implies선택이 다른 후보를 유도하지만 자동 강제하지 않음장문 역할은 조건부 로더를 권고
forbids둘을 동시에 쓸 수 없음서로 다른 단일 소유 훅 경로
substitutes하나가 다른 기전을 충분히 대체검증된 기존 통제가 있으면 같은 통제를 중복 설치하지 않음
synchronizes같이 버전·갱신돼야 함역할 정본과 provider별 생성물
bounds안전·비용 상하한을 둠사용자 기본 모델 프로필은 자동 실행 상한
trades_off한쪽 증가가 다른 비용을 키움검토 폭과 토큰·시간
shares_budget여러 요소가 같은 한정 자원을 사용문맥·검토자 수·영수증 검토가 잔여 토큰을 공유
erodes선언은 유지되지만 다른 요소가 실효를 깎음느린 훅이 우회를 늘려 실제 강제력을 낮춤
common_mode같은 원인으로 방어층이 함께 실패같은 adapter가 gate·router·receipt를 모두 오염
compensates한쪽 축소에 보완 장치가 필요짧은 문맥 대신 명시적 검색·영수증 강화
invalidates변경이 기존 증거를 무효화훅 변경은 과거 설치 검증 영수증을 무효화
derives정본에서 생성됨공통 역할 정의에서 provider별 역할 파일 생성
verifies별도 관측으로 주장을 시험설치 후 실제 훅 경로와 실행 결과 확인

단순 양·음 상관으로는 부족하다. 조건, 방향, 강도, 적용 범위, 우선순위, 출처, 버전, 충돌 해결권자를 가진 제약으로 표현한다.

특히 erodes와 common_mode는 켜짐/꺼짐으로 환원하지 않는다. 선언상 활성인 통제가 우회·공통 의존 때문에 약해질 수 있기 때문이다. 관계 그래프는 설정값뿐 아니라 우회율, 오류 상관, 실제 발화처럼 실효값을 관측해야 한다.

6.3 구성 합성 계약

  1. 관측 — 파일과 런타임에서 현재 상태를 읽되 아무것도 쓰지 않는다.
  2. 분류 — 관측 사실, 추론, 사용자 의도, 미확인을 분리한다.
  3. 제약 해석 — 필수·배제·동기화·상쇄·예산·권한 관계를 계산한다.
  4. 최소 질문 — 관측으로 결정할 수 없고 결과를 실제로 바꾸는 것만 사람에게 묻는다.
  5. 후보 구성 — 선택 결과뿐 아니라 따라오는 추가·삭제·비활성화와 이유를 보여준다.
  6. 영향 검토 — 기존 시스템 소유권, 안전 하한, 외부 효과, 복구 한계를 확인한다.
  7. 계획 고정 — 승인된 계획의 입력 snapshot과 해시를 고정한다.
  8. 원자 적용 — 허용된 경계 안에서 적용하고 부분 실패 증거를 보존한다.
  9. 독립 검증 — 생성한 계획과 다른 관측 경로로 실제 적재·실행·결과를 확인한다.
  10. 지속 재평가 — 환경 변화가 제약 해를 무효화하면 조용히 바꾸지 않고 새 후보를 만든다.

자원이 줄었다고 필수 안전 장치를 자동으로 제거하지 않는다. 선택 문맥 축약, 작업 분할, 낮은 비용 프로필 추천은 가능하지만 안전 하한을 만족할 수 없으면 BLOCKED 또는 PENDING_APPROVAL로 멈춘다.

6.4 제약을 다시 제약한다 — anti-ratchet

안전 규칙도 비용과 권력을 만든다. 사고가 날 때마다 금지와 승인 단계를 더하기만 하면 시스템은 안전해지는 대신 합법적인 작업까지 막고, 사용자는 우회 경로를 만든다. 따라서 제약은 영구 불변식이 아니라 다음 계약을 가진 1급 정책 객체다.

  • 보호하려는 실패와 근거
  • 적용 범위와 발동 조건
  • 제약의 소유자, 승인자, 이의제기·재심 경로
  • 예상 비용과 실제 false block·blocked-safe-work 측정치
  • 만료·재검토 시점, 완화·삭제 기준
  • 안전한 예외 또는 break-glass 조건과 보상 검증
  • 다른 제약과 결합해 생기는 교착·공통모드

즉시 실패를 막는 안전 하한도 조용히 우회할 수는 없지만, 왜 그 하한이 존재하며 언제 다른 기전으로 대체할 수 있는지는 검토 가능해야 한다. fail-closed가 복구 경로까지 닫아 영구 교착을 만들면 안전 성공이 아니다. 격리, 읽기 전용 진단, 별도 승인 복구처럼 위험을 넓히지 않는 탈출 경로를 설계한다.

안전 하한은 몰래 낮추지 않는다. 그러나 하한을 지키는 방법은 검토하고 바꿀 수 있다. 일반 제약은 만료·완화·삭제될 수 있지만, 안전 하한은 같은 위험을 맡는 다른 기전이 검증됐을 때만 바뀐다.

8. 권력과 책임 경계

  • AI는 사실을 조사하고 후보·대안·영향을 제안할 수 있다. 불명확한 사람의 의도나 조직의 정당성을 스스로 확정하지 않는다.
  • 더 강한 모델은 더 넓은 권한을 자동으로 얻지 않는다. 모델 능력과 실행 권한은 별도 축이다.
  • 제공자별 사용자 기본 모델·추론 프로필은 자동 실행 상한이다. 이를 넘는 프로필은 이유, 비용·시간·데이터·권한 차이를 보여주고 승인받는다.
  • 필요한 안전 하한이 상한보다 높으면 낮은 프로필로 강행하지 않는다.
  • requested/effective 모델, 추론 강도, 도구, 권한, 폴백을 기록하며 조용한 상향·하향·폴백을 금지한다.
  • 정책 작성자, 승인자, 검증자, 시스템 관리자가 같은 이해관계에 묶이면 형식적 역할 분리는 독립성으로 인정하지 않는다.
  • repo owner와 피해 당사자가 다를 수 있다. 팀·조직 적용 전에는 이의제기, 재심, 철회 권한을 별도로 설계해야 한다.

초기 모델 라우터의 권한은 추천, 부족 감지, 상한 초과 승인 요청, 불일치 차단, 영수증에 한정한다. 자동 선택은 심각도 가중 false-low-risk와 escalation calibration이 검증된 뒤에만 넓힌다.

9. 시스템 불변조건

  1. 조사와 변경 분리 — 진단은 쓰지 않는다.
  2. 출처와 상태 분리 — 관측, 확인된 사실, 추론, 결정, 미확인을 섞지 않는다.
  3. 기존 소유권 보존 — 모르는 기존 파일·훅·정책을 덮거나 제거하지 않는다.
  4. 후보와 활성 분리 — 새 증거와 새 규칙은 자동으로 활성화되지 않는다.
  5. 계획-적용 일치 — 승인 후 입력이 바뀌면 재계획한다.
  6. 경계 제한 — repo 밖 또는 승인 범위 밖 변경은 금지한다.
  7. 검증된 무행동 — not-applicable, not-triggered, not-run, blocked, unverifiable을 성공과 구분한다.
  8. 독립 postcondition — “명령 성공”이 아니라 실제 파일·Git 설정·실행 효과를 확인한다.
  9. 부분 실패 보존 — 실패 증거를 지우고 성공을 선언하지 않는다.
  10. 가역성 정직성 — 되돌릴 수 없는 외부 효과를 rollback으로 부르지 않는다.
  11. 안전 하한 우선 — 자원 부족과 편의가 필수 하한을 조용히 낮추지 않는다.
  12. 민감정보 최소화 — 로그·영수증·프롬프트에 시크릿과 불필요한 개인정보를 남기지 않는다.
  13. 반증 가능성 — 실패가 핵심 주장을 실제로 축소하거나 폐기할 수 있어야 한다.
  14. 제약의 비영구성 — 제약마다 근거·비용·재심·만료·대체 조건을 둔다. 추가만 되고 제거되지 않는 안전 규칙을 정상으로 보지 않는다.

11. 외부 비교 사례 — Exord-init

2026-09-21 현재 공개된 Exord-init 한국어 README, 안전 계약, 프로토콜 계약을 설계 비교 자료로 검토했다. 이는 README와 공개 계약의 검토이며 구현 전체에 대한 독립 검증은 아니다.

가져와 실험할 가치가 큰 기전은 다음과 같다.

  • 대화형 Skill과 결정적 mutation 엔진의 권한 분리
  • 의도 → canonical plan hash → 그 계획에 결합된 승인 → 대상 재검사 → 적용의 연결
  • rooted filesystem, symlink 거부, create-only/원자 publication 같은 경로 안전
  • 미완료 run을 숨기지 않는 journal·복구 검사와 별도 복구 승인
  • 모르는 schema·validation과 미구현 기능의 명시적 실패
  • QUICK이 질문은 줄여도 안전 검사는 줄이지 않는다는 분리
  • bounded inventory와 민감값 대신 수치만 보고하는 방식

그대로 보편 규칙으로 가져오지 않을 것은 다음과 같다.

  • “현재 대화의 한 사용자만 승인 가능”을 팀·조직의 영구 권한 모델로 만드는 것
  • 빈 디렉터리/allowlist CREATE 제약을 모든 도입 모드의 상한으로 만드는 것
  • 판독 불가 run 하나가 범위와 기한 없이 모든 새 작업을 막게 하는 것
  • --yes 부재, 특정 런타임, create-only 방식, 특정 TASK.md 위치를 개념 불변식으로 만드는 것
  • 모든 불확실성에 동일한 fail-closed를 적용하고 안전한 격리·축소 실행 경로를 없애는 것

이 비교가 주는 핵심은 “더 많은 제약”이 아니다. 결정적 mutation에는 강한 계약을 쓰되, 각 제약의 목적·범위·비용·재심·삭제 조건까지 함께 모델링해야 한다는 것이다.

12. 허용되는 주장과 금지되는 주장

현재 허용되는 주장은 다음과 같다.

  • 저장소 범위의 주장-통제 추적과 거짓 무행동 식별을 개선할 가능성이 있다.
  • 관계형 구성 합성과 후보/활성 정책 경계는 검증할 가치가 있는 연구 가설이다.
  • 최소 트랜잭션 안전은 외부 설치 실험의 선행조건이다.

현재 다음을 주장하지 않는다.

  • 사람의 의도를 컴파일한다.
  • 그래프와 영수증이 진실·안전·정당성을 보증한다.
  • Git 저장소가 전체 사회기술 체계의 정본이다.
  • rollback이 이미 소비·전파된 모든 효과를 복원한다.
  • 다중 AI가 본질적으로 독립적이다.
  • 모델 라우터가 최소 충분 프로필을 이미 정확히 안다.
  • PDD 사례만으로 범용성·독창성·장기 효과가 입증됐다.

13. 개념이 살아남는 조건

이 체계는 최강의 기존 도구 조합과 같은 자원 조건에서 비교한다. 다음 중 하나가 반복되면 개념이나 범위를 축소한다.

  • 관계 모델을 제거해도 안전·정확성·판단 비용이 유의미하게 나빠지지 않는다.
  • 문서·역할·검사 수만 늘고 실제 적재·실행·시정조치가 개선되지 않는다.
  • 다양한 repo에서 질문과 설정 충돌이 늘어 수동 구성보다 순비용이 커진다.
  • 다중 AI 수가 늘어도 오류 상관이 줄지 않는다.
  • 정책이 축적되지만 폐기·만료·재개봉이 작동하지 않는다.
  • 사용자가 체계를 우회하는 shadow process가 늘고 시정조치 종결률이 개선되지 않는다.
  • 제약 수와 차단 시간은 증가하지만 실제 사고·복구 지표는 개선되지 않는다.

다음은 평균 성능으로 상쇄할 수 없는 즉시 실패다.

  • 승인 없는 정책 활성화 또는 무권한 변경
  • repo 경계 밖 변경
  • 거짓 VERIFIED
  • 민감값 유출
  • 필수 안전 하한을 알리지 않고 낮춘 실행

구체 실험과 판정 순서는 docs/실험_계획.md가 정한다.
